## 🧠 学到 / 想明白的

- Git 基本工作流：`diff` → `commit` → `push` → PR。
- DDD(领域驱动设计)。
- AI 的三种机制：参数机制(基础知识)、推理机制(推理得到的知识)、联网机制(前两种机制都拿不到时用来获取信息)。
- 从 0 到 1 时 AI 能帮忙搭架构(需求不复杂时够用)，但做到半成品要改需求/加功能时，真正考验的是开发者自己会不会编排架构、懂文件职责和耦合关系——这是看朋友用 Codex 做发邮件自动化引发的思考。

## 🧭 复盘启发

- 这周想让 AI 一口气重写 8 个文件推送 GitHub，结果大文件(1000+ 行)超 token 失败，只能自己手动改——这其实是“改动粒度太粗”的信号。下周可以在改大文件前先按功能拆成更小的提交，既避免超 token，也顺便练“编排+耦合”直觉。
- 用 XMind 先梳理壳牌 SDCC 架构、再动手重构，这个“先画图再动手”的顺序很值得固定下来——建议以后每次开新一轮重构或新功能前，花 10-20 分钟画一版架构图/数据流图存到项目页面，而不是只在脑子里过一遍。
- 这周入职培训占了不少时间，主线(壳牌重构)进展偏“梳理”而非“落地”。下周拿到 API key 后，建议先挑一个小范围(比如一种订单类型)把接口传数据的方式跑通，验证可行再铺开，别一上来就大改。
- 这周刚学的 DDD(领域驱动设计)正好能用在你现在做的“清理死代码 + 统一命名”重构上——可以试着用它的“边界上下文”概念，给 `services.config`、`core.uploader` 这些模块理一下职责边界，看命名统一之后模块边界是不是也跟着清楚了。
